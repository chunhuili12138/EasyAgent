## 功能概述

**触发器管理**负责配置工作流的执行入口。定时任务、Webhook 和内部事件会启动工作流；**审批提供方不会启动工作流**，它只接收外部审批结果，并用 `correlationKey` 恢复已经停在审批等待节点的运行。

新建记录保存后默认停用。请先核对配置并完成联调，再手动启用。

## 如何选择类型

| 业务需求 | 类型 | 谁发起 | 是否启动新运行 |
|---|---|---|---|
| 按固定日历时间执行 | 定时任务 | EasyAgent 调度器 | 是 |
| 第三方系统通过公网接口通知 | Webhook | 外部系统签名 POST | 是 |
| EasyAgent 内部模块发布业务事件 | 内部事件 | 已认证的平台接口 | 是 |
| 第三方系统返回某次审批结果 | 审批提供方 | 外部系统签名 POST | 否，只恢复等待节点 |

如果第三方系统需要主动启动流程，请使用 Webhook；不要把审批提供方当成 Webhook 使用。

## 适用角色与前置条件

- **适用角色**：拥有自动化触发器查看或管理权限的租户 Agent 管理员。
- **共同前置条件**：自动化引擎已启用，目标工作流已经发布。下拉框只显示已发布工作流。
- **外部回调前置条件**：第三方系统能够保持原始 JSON 正文不变，并计算 HMAC-SHA256 签名。

## 进入路径

主菜单：**自动化中心 -> 触发器管理**。

页面顶部可切换 **定时任务 / Webhook / 内部事件 / 审批提供方**。列表中的工作流显示“名称（编码）”，而不是数据库 ID。

## 通用创建步骤

1. 先在**工作流设计**完成校验和发布。
2. 进入**触发器管理**，在顶部选择正确类型。
3. 点击右上角**新建**，选择目标工作流，填写能说明业务用途的名称。
4. 按所选类型完成下文配置，点击**保存**。
5. 核对列表中的触发配置。新记录默认停用，确认无误后点击操作列中的启用按钮。

触发器每次执行时使用该工作流当时的最新发布版本；重新发布工作流后无需重建触发器。

## 配置定时任务

1. 切换到**定时任务**，点击**新建定时任务**。
2. 选择已发布工作流并填写名称。
3. 在**执行频率**选择预设，或选择自定义后填写 Spring Cron。
4. 选择 IANA 时区，例如 `Asia/Shanghai`。
5. 设置误触发窗口和重叠策略。
6. 在**工作流输入**、**运行变量**页签填入 JSON 对象；点击示例可快速生成结构。
7. 保存后核对列表中的 Cron、时区、重叠策略和下次执行时间，再启用。

### 定时字段

| 字段 | 范围/示例 | 说明 |
|---|---|---|
| Spring Cron | `0 0 9 * * *` | 六段顺序是“秒 分 时 日 月 周” |
| IANA 时区 | `Asia/Shanghai` | 调度器按此时区计算执行时刻 |
| 误触发窗口 | 0-86400 秒 | 服务恢复后允许补偿的最大延迟；`0` 表示错过后不补偿 |
| 重叠策略 | `SKIP` 等 | 同一触发器已有活动运行时如何处理新计划 |
| 工作流输入 | JSON 对象 | 每次固定写入 `workflow.input`，必须符合工作流输入 Schema |
| 运行变量 | JSON 对象 | 每次固定写入 `workflow.variables`，适合环境、执行人和开关参数 |

常用表达式：

| 频率 | Cron |
|---|---|
| 每 5 分钟 | `0 */5 * * * *` |
| 每小时整点 | `0 0 * * * *` |
| 每天 09:00 | `0 0 9 * * *` |
| 每周一 09:00 | `0 0 9 * * MON` |
| 每月 1 日 09:00 | `0 0 9 1 * *` |

“每 30 天”预设实际是每月 1 日执行，并非严格间隔 30 x 24 小时。

### 重叠策略

| 策略 | 行为 | 建议 |
|---|---|---|
| `SKIP` | 活动运行未结束时跳过本次 | 默认选择，适合不可并发任务 |
| `QUEUE` | 活动运行结束后合并补执行一次 | 适合允许延迟但不想丢执行机会的任务 |
| `PARALLEL` | 新旧运行并行 | 只用于确认并发安全的流程 |
| `REPLACE` | 取消活动运行并启动新运行 | 外部写操作慎用，必须评估中途取消影响 |

## 配置 Webhook

Webhook 供第三方系统通过签名 POST 启动工作流。

1. 切换到 **Webhook**，点击**新建 Webhook**。
2. 选择已发布工作流并填写名称。
3. 设置 30-3600 秒的签名时间窗口。窗口越小，防重放能力越强，但双方服务器时间必须同步。
4. 在 **Payload Schema** 中声明外部 JSON 正文的结构。
5. 在**工作流输入**和**运行变量**配置每次固定传入的值。
6. 保存后立即复制一次性弹窗中的公开键、回调路径和签名密钥。
7. 将相对回调路径拼接到外部可访问的后端域名，完成签名请求联调，再启用 Webhook。

外部正文不会自动合并到 `workflow.input`。工作流节点应从 `trigger.payload.<字段>` 读取正文，例如 `trigger.payload.orderNo`。

### Payload Schema 示例

```json
{
  "type": "object",
  "required": ["orderNo", "approvedAt"],
  "properties": {
    "orderNo": { "type": "string" },
    "approvedAt": { "type": "string" }
  }
}
```

正文不符合 Schema 时返回 `422`，不会启动工作流。

## 配置内部事件

内部事件只供 EasyAgent 内部已认证接口发布，不是第三方公网 Webhook。

1. 切换到**内部事件**，点击**新建内部事件**。
2. 选择已发布工作流并填写名称。
3. 填写稳定的事件类型，例如 `after_sales.refund_approved`。
4. 使用 **Payload Schema** 声明 `payload` 业务对象结构。
5. 配置固定工作流输入和运行变量，保存并启用。
6. 使用当前租户下拥有 `AGENT_ADMIN` 或 `SYS_ADMIN` 权限的身份调用 `POST /api/automation/events`。

事件类型保存时会转为小写，并且必须匹配 `[a-z][a-z0-9._:-]{2,99}`。发布请求示例：

```json
{
  "eventId": "refund-approved-RF20260805001",
  "eventType": "after_sales.refund_approved",
  "occurredAt": "2026-08-05T09:30:00Z",
  "payload": {
    "refundNo": "RF20260805001",
    "orderNo": "SO20260801018"
  }
}
```

工作流中的完整触发包位于 `trigger.payload`：事件编号在 `trigger.payload.eventId`，业务对象在 `trigger.payload.payload`，因此订单号路径是 `trigger.payload.payload.orderNo`。

## 配置审批提供方

审批提供方用于“工作流已经运行到等待节点，第三方系统稍后返回审批结果”的场景。它本身不创建新运行。

由于创建审批提供方时必须选择已发布工作流，而等待节点又需要提供方 ID，首次配置按以下顺序完成：

1. 先发布一个可用的基础工作流版本。
2. 进入**触发器管理 -> 审批提供方**，新建提供方并保持停用。
3. 保存一次性弹窗中的**审批提供方 ID**、公开键、回调路径和签名密钥。
4. 回到**工作流设计**，在审批等待节点填写提供方 ID、唯一关联键路径、超时和超时出口。
5. 重新校验并发布工作流。
6. 回到触发器管理启用审批提供方。
7. 启动一次工作流，使其进入等待状态，再让第三方系统发送签名回调。

回调正文至少包含：

```json
{
  "correlationKey": "refund-RF20260805001",
  "status": "APPROVED"
}
```

- `correlationKey` 必须与活动等待节点注册的值完全一致，长度 1-128，仅允许字母、数字、点、冒号、下划线和连字符。
- `status` 仅支持 `PENDING`、`APPROVED`、`REJECTED`，不区分输入大小写。
- `PENDING` 记录结果但不恢复流程；`APPROVED` 和 `REJECTED` 按等待节点分支恢复。

如果没有匹配的活动等待记录，回调返回 `404`。这通常表示提供方 ID、关联键或目标租户不一致，或者该等待已经结束。

## Webhook 与审批签名

两种外部回调使用相同签名协议，正文最大 1 MB。必须发送以下请求头：

| 请求头 | 内容 |
|---|---|
| `X-Automation-Timestamp` | 当前 Unix 秒时间戳 |
| `X-Automation-Event-Id` | 本次事件的唯一 ID，1-128 个允许字符 |
| `X-Automation-Signature` | `v1=` 加 HMAC-SHA256 十六进制结果 |

签名原文必须使用**收到的原始字节正文**：

```text
timestamp + "." + eventId + "." + rawBody
```

计算方式：

```text
signature = "v1=" + hex(HMAC-SHA256(signingSecret, signingText))
```

不要先解析再重新序列化 JSON；空格、换行或字段顺序变化都会导致签名不同。外部机器应使用 NTP 校时，并在页面配置的签名窗口内发出请求。

## 数据位置说明

| 来源 | 工作流路径 | 是否自动合并 |
|---|---|---|
| 页面配置的工作流输入 | `workflow.input` | 独立对象 |
| 页面配置的运行变量 | `workflow.variables` | 独立对象 |
| Webhook JSON 正文 | `trigger.payload` | 不合并到输入或变量 |
| 内部事件元数据 | `trigger.payload.eventId/eventType/occurredAt` | 不合并 |
| 内部事件业务对象 | `trigger.payload.payload` | 不合并 |
| 定时触发元数据 | `trigger.payload.scheduledAt/triggerId` | 不合并 |

如果工作流需要把外部字段传给节点，应在工作流设计中显式配置输入映射，不要在固定输入中重复写占位数据。

## 启用、停用与轮换密钥

- **启用**：开始接受新的计划或外部请求。启用时目标工作流必须仍有已发布版本。
- **停用**：不再创建新运行或接受新回调；已经运行中的实例不会被自动取消。
- **轮换密钥**：仅 Webhook 和审批提供方支持。旧密钥立即失效，必须同步更新第三方系统。
- 公开键和回调路径用于路由请求，可以提供给调用方；签名密钥必须保存到密钥管理系统，不能写进日志、工作流参数或普通文档。

## 验收步骤

### 定时任务

1. 启用后确认列表显示合理的下次执行时间。
2. 到达执行时间后，在**运行实例**找到新的运行，并核对触发类型和目标工作流。
3. 验证误触发和重叠策略符合预期。

### Webhook

1. 发送一条合法签名请求，首次响应应为 `202`，并返回运行 ID。
2. 使用相同事件 ID 和完全相同正文重发，应返回 `200` 和原运行，表示幂等命中。
3. 使用相同事件 ID但不同正文重发，应返回 `409`。
4. 在运行详情核对节点从 `trigger.payload` 读取到正确字段。

### 内部事件

1. 发布接口返回事件记录后，在**事件记录**确认 Outbox 状态。
2. 等待异步匹配，再到运行实例确认工作流启动。
3. 核对业务字段路径是 `trigger.payload.payload.<字段>`。

### 审批提供方

1. 确认工作流先进入审批等待状态。
2. 使用匹配的 `correlationKey` 发送 `PENDING`，工作流应继续等待。
3. 发送新的事件 ID 和 `APPROVED` 或 `REJECTED`，工作流应进入对应分支。
4. 在运行时间线和事件记录中核对等待、回调和恢复顺序。

## 常见问题

**为什么工作流不在下拉框中？**
下拉框只加载已发布工作流。回到工作流设计完成校验和发布后，再刷新触发器页面。

**保存后为什么没有开始执行？**
新建记录默认停用。请核对配置后手动启用；定时任务还要检查时区和下次执行时间。

**Webhook 返回签名错误怎么办？**
检查三个请求头、Unix 秒时间戳、公开键、当前密钥以及原始正文。签名必须对实际发送的字节计算，不能签名后再格式化 JSON。

**为什么配置了工作流输入，却读不到 Webhook 字段？**
固定输入和外部正文是两个对象。固定值从 `workflow.input` 读取，Webhook 正文从 `trigger.payload` 读取。

**内部事件为什么没有立即生成运行？**
内部事件先写入 Outbox，再异步匹配触发器。到事件记录检查接收、匹配和失败状态；它不是同步 Webhook。

**审批回调为什么不启动工作流？**
这是预期行为。审批提供方只恢复已经等待的实例。需要从外部系统启动新流程时请改用 Webhook。

**事件 ID 可以重复吗？**
相同事件 ID 与完全相同内容会返回原结果；相同 ID 但不同内容会返回冲突。每次新的业务事件应使用新的稳定 ID。

## 使用边界

- 触发器只运行目标工作流的最新发布版本，草稿不会参与执行。
- Webhook 和审批只接受 JSON POST，请求正文上限为 1 MB。
- 内部事件需要当前租户内的认证权限，不能替代第三方签名 Webhook。
- 并行和替换策略不会自动保证外部 API 幂等；工作流包含新增、退款等写操作时，外部接口仍需实现幂等保护。
- 不要为了“测试成功”删除失败事件或失败运行；这些记录是定位签名、Schema、映射和外部接口问题的执行证据。
